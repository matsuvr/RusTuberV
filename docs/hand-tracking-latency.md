# 手の動き始めと再捕捉の遅延

2026年11月10日、Windowsで腕交差と上げ下げの録画を再生した。取得した `origin/main` は調査基準の `8cb06830fa6b7b59b785aed331793b4ebd715835` と一致した。計測を加えた基準版は `a5208956a0a1dd982af072debe083509f3b61cb4`、応答を変更した測定版は `d1c3ad3f97a98782d660d3f76cfbac51c5ebe6ba`。以下はこの比較で測った値である。

## 腕の応答を変えた箇所

基準版では、目標と表示位置の差が腕長の5%以内なら、手首XYの時定数は125 ms、肘は150 msのままだった。再捕捉時は腕に観測の重みが戻る500 msの間も、低速応答の残り時間を更新していた。重みが1になってからも、残差が大きいと手首は最長750 ms、肘は900 ms、この時定数で動き続ける。その間も通常の時定数で腕は動く。頭の回転フィルターの標準時定数は25 msで、各時定数と最終骨の到達時間は異なる。

`ArmPositionSmoother` は、手首と肘でそれぞれ `PlanarMotion` を持つ。`observed` は採用した肩基準のXY差分を撮影時刻の差で割り、速度ベクトルを60 msの一次遅れで平滑化する。速度を `v` とすると、XYの時定数は `max(0.040, quiet_tau / (1 + 2.0 * |v|²))` 秒。速度の単位は校正済み腕長/秒、係数2.0の単位は秒²/腕長²である。小さい静止ノイズに対する帯域の変化を抑えつつ、変位が5%に達する前から移動に応答する。

観測を消費するのは新しい画像の採用時だけで、同じ観測を保持する描画tickでは速度を更新しない。実際の欠測や採用棄却で該当関節の速度履歴を切る。復帰後の最初の観測は次の速度差分の起点になる。描画ごとの位置更新には従来の二段一次遅れの厳密解 `cascade_step` を使い、Zには元の時定数を使う。外挿は行わない。

初回は信頼できる観測が4件続くと腕の採用ゲートが開き、同じ観測が校正の1件目にもなる。連続して採用できる場合は8件目で5サンプルが揃う。消失を認めるまでの6件、再捕捉を確認する2件の条件は従来どおり。以前追っていた腕が実際に失われた場合だけ、`ArmTrackingProfile::reacquire_position` で手首と肘の重みを現在値から200 msで戻す。初回と掌・指・胸郭・顔の復帰には各従来値を使う。

## 二つの測定方法

- **同じ画像列を推論する比較**では、`data/video/WIN_20261004_22_48_07_Pro.mp4`（腕交差、31.57秒）と `WIN_20261004_22_29_52_Pro.mp4`（上げ下げ、60.60秒）をRGB8・640×360・30 Hzにそろえた。各版・各動画を3回ずつ、既存の `measure-replay.ps1` で再生した。Sapphy.vrm、同一の初期姿勢、毎回未校正、鏡映あり、1920×1080・FIFO、Rich Lookオフ。Core i9-13900、RTX 4090、Vulkan、アプリとBevyのプールに3論理CPUを割り当てた。性能集計は開始5秒以降。比較用出力のPNG・JSON保存は計測終了後に行う。
- **同じ観測列で追跡する比較**では、各動画の基準版1回目で、フィルター直前の `PoseArmFrame`、採用を試みた時刻、顔のアバター入力、描画間隔、表示座標系と入力モードを描画tickごとに保存した。保持、未検出、結果未到着を区別して再生し、両版とも前のtickのIKを次のtickで受け取った。表の姿勢はVRMの最終グローバル変換から読んだ。初回・再捕捉の評価は開始5秒以内も含む。固定再生の実行速度は性能値から除いた。

Windows実カメラの `captured_at` はMSMFの `camera.frame()` がバッファを返した直後、画素をデコードする前の単調時計である。録画では `ReplaySource` を開いた時刻に `source_seq / 30` 秒を足した予定画像時刻を使う。`PoseInferenceTrace` はバックエンド入口と、画像変換後のPose呼び出し、同一画像のHand呼び出しの開始・終了を保持する。Poseが人物を検出しないときはHandの区間・検出数ともに欠測。Handを実行したときの検出数と、左右への対応付け後の手首XYを別に記録する。Handの左右ラベルのスコアは座標の信頼度に使わない。

描画側の受領時刻は新しい画像番号を初めて消費した `sampled_at`。画像に対応する肩・肘・手首のworld座標とvisibilityは `observations.json` にある。`frames.jsonl` には採用ゲート、校正件数・腕長、採用した手首、平滑化後の手首・重み、最終関節がある。`arm_observation.source_seq` は追跡入力、`arm_source_seq` は同じ目標で再利用した解を含む採用番号。変更版の `displayed_path_seq` は補間を実際に進めて表示したIK経路の入力番号で、後続の推論結果が届くだけでは進まない。

## Hand画像座標を使う案

同一画像で対応付けた一つの候補から、手を中心とするworld点群と画像上の手首XYを一緒に取り出した。画像XYは左上原点、右・下が正で、画面外の値も保持する。掌と指は引き続きHandのworld点群から求める。

試験では画像XYを `q = (u × 幅/高さ, v)` に変換した。肩→肘・肘→手首の各区間について、Pose worldのメートル単位のXY差分を `p`、画像上の差分を `Δq` として、`Σ(Δq · p) / Σ|Δq|²` で正の倍率を推定した。腕長校正と同じ5件の中央値を各側で固定。Hand手首とPose肩の差にこの倍率を掛けて腕長で割り、Yだけ反転した。ZはPose worldの肩と手首の差から従来どおり求めた。手が対応付かなかった画像では位置観測を欠測とした。

固定した倍率（m/画像高さ）は腕交差で左0.516・右0.577、上げ下げで左0.462・右0.477だった。腕交差の対応付き観測で、Handから変換したXYと同時刻のPose worldを腕長単位で比較すると、差のp95は左0.308・右0.248。これは二つの位置推定の食い違いで、どちらかの絶対的な位置誤差を測った値ではない。Handを実行して検出数が0の画像は182枚。1個以上検出したものの当該側との対応が得られなかった画像は左18・右30枚だった。

同じ観測列、同じ速度応答と200 ms復帰で位置供給元だけを変え、両候補を同じdevビルド条件で最終骨まで比較した。上げ下げではHand方式の最終手首の10 / 50 / 90%は54.392 / 54.521 / 54.680秒。90%はPose方式より113 ms早かったが、動き始めの10%は28 ms遅かった。腕交差の最初の交差もPose方式の2.087秒から2.492秒へ遅れた。一方、6秒付近の短い交差はHand方式で再現した。動き始めの改善に一貫性がなく、位置変換による振幅の違いも大きいため、今回の手首目標にはPose worldを採用した。画像座標と対応付け前の個数は診断に残した。

変更版でも `-Tag hand-fixed-new` で同じ観測を再生する。測定ツールのあるPR版では、次のように集計できる。

## 実カメラで残る確認

Windowsで上記Sapphyを選び、両版で同じカメラ・解像度・30 Hz・照明・初期姿勢を使って校正する。通常描画、NDIとLooking Glassオフで、静止→腕長5%未満の小移動→大移動→停止→反転→片手を3秒隠す→戻しながら動かす→腕を止めたまま体幹を左右に移す、の短い録画を1本作る。その録画を上記と同じ手順で両版に入力し、動き始め、交差時の左右、再捕捉後の10/50/90%、停止後の行き過ぎ、肩・肘・手首の揺れを比較する。

カメラの露光からドライバ受領までと、最終骨の反映からモニター表示までの遅れは未測定。体幹だけの移動やカメラ距離を変えた場合も、今回の2本では単独の条件として評価できない。実際の人物とモニターを同じ高フレームレートの外部カメラに収めると、実表示までの顔と手の差をフレーム数で比較できる。
